# QuantEdge AI — Validation Protocol

Status: **Phase 0.5 revision** (2026-11-01). Binding: no performance or profitability figure is published in this
repository unless this protocol produced it and its run manifest is stored. No such figure exists today.

---

## 1. Three separate evidence streams

| Stream | Data | Purpose | Who may look |
|---|---|---|---|
| **Model selection (development)** | Burn-in + development folds | Build, tune, choose, calibrate | Freely, inside the protocol |
| **Final holdout** | 2025-01-01 → end of research data (~Roland Garros 2026) | One unbiased estimate per major model version | Locked. Opened only through a logged command (§2.3) |
| **Prospective paper trading** | Forward from first own odds capture | Only evidence about real-time, timestamped decisions | Append-only ledger. Never used for model selection retroactively |

The three streams never mix. A configuration selected after seeing holdout or paper results counts as a new
version and needs **new** untouched data.

## 2. Partitions and walk-forward

### 2.1 Partitions (D-05)
| Partition | Period | Use |
|---|---|---|
| Burn-in | earliest → 2004-12-31 | State warm-up only. Never scored |
| Development | 2005-01-01 → 2024-12-31 | Walk-forward folds (§2.2). The final two years (2023–24) are a *late check* with a logged look count |
| Sealed holdout | 2025-01-01 → research-data end | §2.3 |
| Prospective | forward capture | §7.5 |

Odds-dependent evaluation runs only where contemporaneous odds exist:
- **Tier C (untimed near-close):** tennis-data, 2001+, with book coverage profiled in P3.
- **Tier B (timestamped):** The Odds API. Development years contain only Grand Slams from 2020–21 and five Masters
  from Aug–Oct 2024. Most Tier B data therefore lies **inside the holdout** (DATA_SOURCES.md §4.2).

### 2.2 Walk-forward (chronological folds inside 2005–2024)

Defined in `configs/splits.yaml` and generated by `quantedge.core.splits`. Every boundary is ≤ 2024-12-31.

| Fold set | Test year *y* | Fit window | Calibration / early-stopping slice | Purpose |
|---|---|---|---|---|
| Inner folds | 2013, 2014, …, 2022 (10 folds) | 2005-01-01 → (y−2)-12-31 | (y−1)-01-01 → (y−1)-12-31 | Model selection, hyper-parameters, thresholds |
| Late check | 2023, 2024 | 2005-01-01 → (y−2)-12-31 | (y−1) | Confirm a frozen selection. At most **3 logged looks** per major version |

- Stateful state (ratings, posteriors) is built from the earliest data, so the burn-in years are available as
  *state* but never as scored rows.
- The first inner fold has a 7-year fit window (2005–2011) and a 1-year calibration slice (2012).

- Expanding window with yearly refits (quarterly as a sensitivity check).
- Fold boundaries snap to tournament weeks. No tournament is split.
- Inside each training window, the last 12 months are the **calibration/early-stopping slice**. Calibrators are fit
  there and nowhere else.
- Hyper-parameter search is nested inside the training window. The fold's test year is never used for any choice.
- Stateful components (Elo, serve/return posteriors) run as one causal pass under the chronology policy
  (ARCHITECTURE.md §5). Only their hyper-parameters are tuned per fold, and each fold's state pass stops at its
  test boundary.

### 2.3 Holdout protocol
- Enforced in code by `DataView(mode="development")` (ARCHITECTURE.md §5.8).
- Pipeline QA may touch holdout rows **only for integrity checks**: schema, duplicates, parse failures, coverage
  counts. Outcome-dependent statistics (win rates, metrics, feature-outcome relationships) on holdout rows are
  forbidden before the holdout is opened.
- Before opening:
  - the model version is frozen (git tag);
  - the evaluation config is committed;
  - the expected report template is fixed.
- After opening:
  - results are reported **regardless of outcome**;
  - the opening is logged in `docs/holdout_log.md` with SHA, date and what was evaluated;
  - any change afterwards is a new version.

## 3. Component-specific evaluation

Every component is judged against the baseline appropriate to **its** task. Bookmaker prices are the benchmark
wherever comparable contemporaneous odds exist, but beating them is required **only** for betting conclusions.

| Component | Task | Baseline(s) | Primary metric | Keep criterion |
|---|---|---|---|---|
| Data pipeline | Faithful canonical tables | n/a | Phase acceptance tests | All pass |
| M0 de-vig | Market → probability | Multiplicative method | Log loss on outcomes (development, odds-covered) | Method choice fixed before P5 |
| M1 Elo | Pre-match P(win) | Coin flip; in-fold logistic on log-rank difference | Log loss; Brier; calibration slope/intercept | Beats rank baseline: mean per-match log-loss gain > 0 with 95% block-bootstrap CI excluding 0 |
| M1 vs market | Context only | De-vigged market on the same matches | Log-loss gap with CI | **Reported, not a gate** |
| M2 serve/return | Next-match serve-point win rate | Tour average; player's raw to-date average | Binomial deviance per point (weighted) | Beats both baselines with CI |
| M3 Markov/MC | Distributions of games, sets, margins given inputs | (a) Analytic identities; (b) empirical distribution conditional on match-probability bucket (fit in-fold) | Correctness tests; PIT uniformity; central-interval coverage; CRPS for total games | All correctness tests pass; coverage within tolerance; CRPS ≤ empirical baseline |
| M3 match winner | Pre-match P(win) | M1 Elo | Log loss | Reported. Gate only if used as a production predictor |
| M4 calibrated ML | Pre-match P(win) | Best of M1/M3 | Log loss with CI; calibration | Beats baseline by a **pre-declared margin** with CI; stable across folds |
| Market-anchored / final | P(win) for betting | **De-vigged market (contemporaneous)** | Log-loss gap; CLV | Required only to proceed to staking analyses |
| Derived-market pricing | Totals/handicap/first set | De-vigged market for the same line (where it exists) | Log loss on binary line outcomes | Testable only where timestamped line odds exist |
| Portfolio | Stake allocation | Flat stake; independent fractional Kelly | Log growth, drawdown, turnover on identical bet sets | Report-only; never a reason to change probabilities |

## 4. Probabilistic metrics

Always computed on identical match sets for model and baseline:
- **Log loss** (primary). Probabilities are clipped to [1e-6, 1−1e-6] and the clip count is reported.
- **Brier** with Murphy decomposition.
- **Calibration:**
  - reliability diagram (equal-mass bins);
  - calibration slope and intercept from logistic recalibration;
  - ECE, which is reported but not used to select.
- AUC (secondary) and accuracy (context only).

**Comparisons:**
- Per-match loss differences are summarised with block bootstrap CIs (blocks = tournament weeks).
- A Diebold–Mariano-style test uses block-robust variance.
- Slices: surface, level, best_of, rank gap, era, favourite/longshot band, players with few prior matches,
  retirement-prone players.

## 5. Orientation and data-integrity statistics

### 5.1 Orientation balance (sample-size-aware)
Orientation is winner-independent **by construction** (ARCHITECTURE.md §4.2). The structural tests (winner-swap
invariance, golden vectors, row-order invariance) are the guarantee. The statistical checks below are a sanity net:

1. **Global exact binomial test.** Under H0, `a_won ~ Binomial(N, 0.5)` over completed **development** matches.
   Fail if the two-sided p-value < α = 0.001.
   - The implied acceptance band is ±3.29·0.5/√N. For example, at N = 100,000 it is about ±0.52 percentage points.
   - The band therefore tightens with sample size instead of being a fixed ±1%.
2. **Stratified homogeneity.** A G-test of `a_won` across year × level strata. Strata with < 200 matches are pooled.
   Holm correction, family α = 0.001.
3. **Covariate balance.** Exact binomial test on `P(player_a is higher-ranked) = 0.5` over matches with both ranks,
   α = 0.001. This detects orientation correlated with strength.
4. **Power check (mutation test).** On a synthetic fixture of 10,000 matches, a deliberately leaky orientation
   ("winner is A" in 55% of matches) **must** fail test 1. This shows the test can detect a 5-point bias at that
   sample size.

The data are fixed and the hash is deterministic, so these tests are deterministic. They are not flaky.

### 5.2 Leakage tests (CI, synthetic fixtures; real-data versions run locally)
1. **Future perturbation.** Mutate every result not in I(m) (ARCHITECTURE.md §5.5). Features and predictions for
   *m* must be byte-identical.
2. **Truncation equivalence.** State for *m* computed from the full history equals state computed from a history
   truncated at *m*'s cutoff (plus the overlay).
3. **Same-day isolation.** Two matches with overlapping day bounds never enter each other's information sets.
4. **Batch order invariance.** Permuting the order within a knowability batch gives identical state.
5. **Antisymmetry.** `p(A,B) + p(B,A) = 1`.
6. **Label shuffle.** With shuffled labels, performance collapses to the base rate.
7. **Forbidden-input scan.** No feature depends on a column tagged `post_match`, and none is fit on post-cutoff rows.
8. **Holdout guard.** A development-mode read of a 2025+ row raises.

### 5.3 Chronology sensitivity
For every stateful model, compare the conservative policy with the naive sequential variant. A large gap is
reported as a leakage-exposure indicator. The conservative variant is always the official one.

## 6. Data and research-integrity checks

**Odds:**
- Overround outside a plausible band (< 1.00 means underround/error; > 1.15 means review).
- Odds ≤ 1.01 or ≥ 100.
- Swapped sides, detected against cross-book consensus.
- Single-book outliers in logit space, which are excluded from execution as potential palpable errors.
- Snapshots after commence time.
- Stale (unchanged) prices.
- Duplicate snapshots.
- Unlinked or ambiguous matches, which are quarantined and counted.

**Missing data:**
- Coverage tables by year × level × field.
- Missingness indicators.
- Imputers fit in-fold only.
- Check whether missingness correlates with outcome.

**Survivorship and selection:**
- Full draws including qualifying and Challengers in the rating state.
- No universe defined by future success or career length.
- The odds-covered subset is compared with the full population, because Tier B covers only big events.
- Match Charting Project data is a biased sample.

**Overfitting and snooping:**
- An experiment registry of every run, including failures.
- The number of configurations tried is reported alongside any result.
- White's Reality Check or Hansen SPA for strategy selection.
- Pre-registered evaluation configs.
- The evaluation module is changed only through reviewed commits, with a hash checked in the run manifest.

## 7. Profitability testing

### 7.1 Evidence tiers (every result is labelled)
| Tier | Odds | Supports |
|---|---|---|
| **A** | Own prospective timestamped capture, paper-traded | "Would have been available at observed prices" (still not proof of acceptance) |
| **B** | Historical timestamped snapshots (The Odds API) + execution model | Simulated backtest under stated assumptions |
| **C** | Untimed near-close (tennis-data, private) | Benchmark only: calibration vs market, closing-line comparisons. **No P&L claims** |

### 7.2 Observed vs executable
- A snapshot is an **observed price**, not an accepted wager.
- Execution is modelled with explicit, **unverified** parameters:
  - decision latency (default 60 s);
  - the snapshot used must be the first with `observed_at ≥ decision_time + latency`, and before commence;
  - slippage haircut on the odds;
  - max stake per book;
  - acceptance probability.
- Every result is reported on a sensitivity grid over these parameters. A result that survives only optimistic
  settings is reported as such.
- Execution is at a **single named bookmaker's** price. Never at Max, Avg, or the median across books.
- Closing prices are used only for CLV and Tier C benchmarks. They are never treated as available earlier.

### 7.3 Settlement
- Retirement, walkover and void rules differ by bookmaker and market. Each rule used must cite its source.
- An unknown rule excludes the bet **before** its outcome is known, never after.

### 7.4 Metrics
- **CLV** is the primary diagnostic: log(odds_taken / de-vigged closing odds) and the share beating the close.
- Bet count, turnover, ROI and log growth with bootstrap CIs.
- A Poisson-binomial test of wins vs implied probabilities.
- Edge retention (realised ÷ predicted edge).
- Max drawdown.
- Results with CIs spanning zero are reported as **inconclusive**.

### 7.5 Prospective paper trading
- Forward-only, append-only ledger.
- Each entry stores the snapshot ID, decision time, model version and manifest.
- No backfilling. No retroactive edits.
- Evaluated only after a pre-declared minimum number of bets.

## 8. Reporting template
1. Run manifest (SHA, data manifests, config, seed, licence lineage).
2. Stream (development / holdout / prospective) and evidence tier.
3. Universe and exclusions with counts and reasons.
4. Component metrics vs the baselines in §3, with CIs.
5. Reliability diagrams.
6. Betting: execution assumptions and sensitivity grid, CLV, ROI CI, drawdown.
7. Number of experiments behind this configuration.
8. Known limitations.
